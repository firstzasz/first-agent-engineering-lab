## Purpose

This is the first mechanism-level comparison for FIRST Agent Engineering Lab.

It does **not** ask which repository is better overall. It asks what reusable engineering mechanisms each approach encodes, where those mechanisms live in the skill anatomy, and which hypotheses are worth testing for FIRST-style work.

The common anatomy is:

`Trigger -> Context -> Procedure -> Tools -> State -> Verification -> Output Contract`

All claims under **Observed** come from static inspection of the pinned source. Claims under **Hypothesis** are not runtime-verified.

## 1. Requirement discovery

### pstack

**Observed sources**

- `pstack/skills/poteto-mode/SKILL.md`
- `pstack/skills/how/SKILL.md`
- prototype routing in `poteto-mode`

**Trigger**

A non-trivial change, architecture decision, uncertainty, or impending user question can route into investigation, `how`, `why`, or a prototype.

**Context**

Repository code, runtime behavior, history, model configuration, and the operator's stated goal.

**Procedure**

The key rule is to classify a question before asking it. If the answer is observable by experiment, the agent should observe it instead of making the operator decide. Genuine product or preference calls stay with the operator.

**Tools**

Read-only exploration subagents, runtime/control tools, prototype execution, history inspection.

**State**

Mostly current task context plus any persistent trail generated by the larger playbook.

**Verification**

An empirical fork should be resolved by observed behavior, not by user preference or model intuition.

**Output contract**

A grounded explanation, observed result, or a narrowed genuine decision for the operator.

### Matt Pocock

**Observed sources**

- `skills/productivity/grilling/SKILL.md`
- `skills/engineering/domain-modeling/SKILL.md`
- `skills/engineering/grill-with-docs/SKILL.md`

**Trigger**

The user explicitly enters a grilling/design-discovery flow.

**Context**

Existing glossary, ADRs, code, facts gathered by subagents, and the evolving design tree.

**Procedure**

Construct a dependency-aware design tree. Ask the whole currently-unblocked decision frontier in rounds. Facts are the agent's job to discover. Decisions belong to the user. Domain terms are sharpened and persisted immediately.

**Tools**

Subagents for factual research, code inspection, project docs.

**State**

The design tree during the session, plus durable `GLOSSARY.md` and selected ADRs when decisions crystallize.

**Verification**

Shared understanding is reached only when the design frontier is empty and the user confirms it.

**Output contract**

Settled decisions, durable terminology, and context ready to become a spec.

### Initial hypothesis

A promising FIRST pattern is **question classification before interruption**:

1. factual or observable question -> agent investigates or prototypes;
2. reversible engineering choice inside an autonomy grant -> agent chooses and records it;
3. genuine product/preference decision -> surface to the operator;
4. durable domain decision -> persist it.

This may preserve Matt's requirement quality without turning routine reversible work into repeated operator checkpoints.

## 2. Architecture and specification

### pstack

**Observed sources**

- `pstack/skills/architect/SKILL.md`
- `pstack/skills/arena/SKILL.md`

**Trigger**

Non-trivial work crossing meaningful boundaries, or explicit architecture/design requests.

**Context**

A traced model of affected subsystems, existing rationale, and multiple candidate designs.

**Procedure**

Ground the current system, generate at least two structurally distinct designs, cross-judge, select a base, graft useful ideas, then implement against the chosen sketch. Redesign rather than patching the sketch if implementation proves the shape wrong.

**Tools**

Parallel subagents, model diversity, worktrees/output paths, architecture exploration.

**State**

Grounding artifacts, candidate designs, synthesis rationale, selected architecture.

**Verification**

The synthesized design must survive implementation and final verification.

**Output contract**

One selected design package with rationale and a verified implementation path.

### Matt Pocock

**Observed sources**

- `skills/engineering/codebase-design/SKILL.md`
- `skills/engineering/domain-modeling/SKILL.md`
- `skills/engineering/to-spec/SKILL.md`

**Trigger**

Designing module interfaces/seams, clarifying domain concepts, or converting established discussion into a specification.

**Context**

Glossary, ADRs, codebase seams, existing tests, and prior conversation decisions.

**Procedure**

Prefer deep modules, small interfaces, useful seams, explicit vocabulary, and testing at the highest viable seam. Convert settled context into a structured spec without re-interviewing.

**Tools**

Code exploration, documentation, issue tracker publication.

**State**

Glossary, ADRs, published spec, testing decisions.

**Verification**

Architecture is partly checked through testability at chosen seams and later spec-aligned review.

**Output contract**

A durable spec expressing problem, solution, user stories, implementation decisions, testing decisions, and scope.

### Initial hypothesis

The mechanisms may combine well:

`domain language + seam/depth criteria + design-twice exploration + durable spec`

The risk is excessive ceremony for small changes. Phase 1 needs an explicit small-change scenario to measure that cost.

## 3. Task decomposition

### pstack

**Observed**

`poteto-mode` maps a task to a playbook and copies playbook steps into a todo list. Multi-step work uses throughput checkpoints and verifiable units.

**Strength visible in source**

The decomposition is closely coupled to task type and execution discipline.

**Potential weakness to test**

The plan may be less durable or queryable across sessions unless paired with a committed trail, PR stack, or other persistent artifact.

### Matt Pocock

**Observed source**

`skills/engineering/to-tickets/SKILL.md`

The method decomposes work into tracer-bullet tickets with explicit blocking edges. Tickets are a task graph, not a sequential checklist. The ready frontier can be worked concurrently. Wide refactors use expand-contract instead of forcing false vertical slices.

**Strength visible in source**

Dependencies and task readiness become persistent and externally inspectable.

**Potential weakness to test**

For a small change, publishing and maintaining the graph may cost more than it saves.

### Initial hypothesis

FIRST may benefit from a threshold rule:

- trivial/small task -> local verifiable checklist;
- multi-session or parallelizable task -> persistent dependency graph in GitHub.

The threshold must be measured, not guessed.

## 4. Debugging

### pstack bug-fix playbook

**Observed source**

`pstack/skills/poteto-mode/playbooks/bug-fix.md`

**Procedure**

Reproduce on the matching surface, binary-search candidate causes, obtain runtime evidence, architect when needed, delegate a narrowly-scoped fix, then verify on the original surface. Failing repro precedes the fix in history when practical.

**Verification**

The original repro must pass on the same surface. Unit tests alone do not prove bug absence.

### Matt `diagnosing-bugs`

**Observed source**

`skills/engineering/diagnosing-bugs/SKILL.md`

**Procedure**

Spend disproportionate effort creating a tight, red-capable feedback loop. Minimise the reproduction. Generate 3-5 ranked falsifiable hypotheses. Instrument one prediction at a time. Convert the minimal repro into a regression test at a correct seam when possible. Re-run the original loop after the fix.

**Verification**

A named command must already have demonstrated the exact symptom and later demonstrate its absence. If no correct regression seam exists, that limitation is itself recorded.

### Initial hypothesis

This looks like a strong hybrid candidate:

`Matt feedback-loop construction + pstack same-surface closure + both approaches' root-cause discipline`

The benchmark should measure time to first valid red signal separately from time to final fix.

## 5. Verification and review

### pstack

**Observed mechanisms**

- `principle-prove-it-works`
- same-surface verification in bug-fix
- sequence-verifiable-units
- `interrogate` multi-model adversarial review
- `show-me-your-work` evidence pointers

The source repeatedly distinguishes a self-report from proof against the real artifact.

### Matt Pocock

**Observed mechanisms**

- TDD and feedback loops
- `code-review` runs Standards and Spec as separate parallel axes
- spec traceability and highest viable test seams

A change can pass repo standards but fail the spec, or satisfy the spec while violating standards. The skill intentionally preserves both verdicts instead of collapsing them.

### Initial hypothesis

A FIRST verification stack may need multiple non-substitutable gates:

1. behavioral test or repro;
2. runtime/artifact verification where relevant;
3. spec/acceptance fidelity;
4. repository standards;
5. evidence persistence.

The experiment should test whether every gate adds signal or whether some are redundant for certain task classes.

## 6. Session continuity and persistent state

### pstack

**Observed sources**

- `session-pickup`
- `show-me-your-work`

Pickup reconstructs branch/worktree state, landed work, open todos, and prior decisions from a trail. It explicitly warns against redoing completed work, then independently verifies inherited claims against the original goal.

The decision trail is append-only and points to evidence such as commits, PRs, traces, or screenshots.

### Matt Pocock

**Observed sources**

- `handoff`
- `wayfinder`
- specs, issues, glossary, ADR conventions

`handoff` compacts conversation state and references existing durable artifacts instead of duplicating them. `wayfinder` stores large planning efforts as a canonical issue map with decision tickets, blockers, a frontier, decisions-so-far, and fog not yet precise enough to ticket.

### Initial hypothesis

For FIRST, durable GitHub state should dominate ephemeral handoff prose.

A likely pattern is:

`persistent task/spec/decision state in GitHub + compact pickup pointer + independent verification of inherited claims`

A temporary handoff file may be useful as a transport artifact but should not become the sole source of truth.

## 7. Autonomy

### pstack `autonomous-run`

**Observed source**

`pstack/skills/poteto-mode/playbooks/autonomous-run.md`

The run begins by defining a checkable exit predicate. It uses event watchers or timed loops, makes the smallest evidence-backed change per iteration, owns reversible side-fixes, logs each checkpoint, and stops only when the predicate is met or a genuine dead end is reached.

The broader mode says reversible work should not block on the human.

### Matt Pocock

**Observed mechanisms**

- `implement-spec` can continuously work the ready ticket frontier with background implementers.
- `wayfinder` explicitly labels decision work HITL or AFK and prevents the agent from impersonating the human side of a genuine human decision.

### Initial hypothesis

A FIRST autonomy policy could combine:

- pstack-style explicit exit predicates and ownership of reversible work;
- Matt-style distinction between facts, AFK work, and genuine HITL decisions;
- hard pause only for irreversible, security-sensitive, or preference/product gates.

This is especially aligned with the lab's existing operating contract, but still requires runtime testing.

## 8. Multi-agent orchestration

### pstack

**Observed sources**

- `swarm`
- `arena`
- `interrogate`
- fresh-subagent rules in `poteto-mode`

Distinct orchestration shapes are explicit:

- **swarm** for partitioned coverage or races;
- **arena** for multiple complete candidates followed by judging and grafting;
- **interrogate** for independent adversarial review;
- fresh subagents to reduce inherited context contamination.

### Matt Pocock

**Observed source**

`implement-spec`

Tickets form a dependency graph. Implementer subagents take ready tickets in separate worktrees. Merger subagents integrate results. New agents launch as the frontier changes. Communication prefers context pointers to copying context.

### Initial hypothesis

These are complementary abstractions rather than direct competitors:

- dependency graph answers **what can run now**;
- swarm answers **how to cover independent slices**;
- arena answers **when multiple full alternatives are worth generating**;
- adversarial review answers **how to challenge a result**.

A future FIRST router may choose orchestration shape based on the dependency structure and uncertainty type.

## Cross-cutting anatomy comparison

| Anatomy layer | pstack tendency | Matt Pocock tendency | Portable mechanism candidate |
| --- | --- | --- | --- |
| Trigger | centralized routing through `poteto-mode` plus explicit skills | explicit user-invoked orchestrators plus model-invoked reusable skills | declarative trigger policy independent of host syntax |
| Context | runtime/code/history exploration, model config, transcripts | glossary, ADRs, specs, issue tracker, code exploration | load the minimum authoritative context needed for the procedure |
| Procedure | playbooks with strong operating rules | smaller composable skills forming a pipeline | procedures should be modular but have a clear composition contract |
| Tools | Cursor Task/cloud, control skills, `/loop`, git/GitHub | Skill tool, issue tracker, worktrees, git, subagents | separate portable procedure from host adapter |
| State | todo/playbook state, branch, transcript, decision TSV | glossary, ADR, spec, tickets, map, branch | persistent state should live in inspectable artifacts, preferably source-controlled or tracker-backed |
| Verification | real artifact, same surface, independent model review, evidence trail | red-capable loop, TDD, spec-vs-standards review | verification should be executable and multi-axis when risks differ |
| Output contract | verified change/PR plus concise evidence and trail | spec/tickets/integration branch/review/handoff | every skill should name what durable artifact the next consumer receives |

## FIRST-fit observations

These are design hypotheses, not benchmark results.

### Likely strong fit

- pstack's refusal to interrupt the operator for empirically answerable or safely reversible work.
- pstack's exit-predicate model for long autonomous runs.
- Matt's distinction between facts the agent must discover and decisions the human must make.
- Matt's persistent dependency graph and frontier for multi-session work.
- Matt's glossary/ADR discipline for durable domain language.
- pstack's same-surface verification and evidence trail.
- Matt's feedback-loop-first debugging.
- pstack's distinct orchestration shapes for swarm, arena, and adversarial review.

### Likely friction to test

- pstack's Cursor-specific orchestration and model configuration may have high host-binding cost.
- Matt's grilling intentionally pauses for human decisions and could become too interactive when the operator already grants autonomy.
- Matt's issue/spec machinery may be excessive for small reversible changes.
- pstack's broad mode can create a large implicit policy surface that may be harder to reason about than explicit small skills.

## Candidate mechanism tests

The next experiments should test mechanisms, not brands:

1. **Question routing:** naive ask-user vs facts-first + decision-frontier policy.
2. **Architecture:** single design vs design-twice + domain/seam rubric.
3. **Decomposition:** local checklist vs persistent dependency graph.
4. **Debugging:** code-reading-first vs tight-feedback-loop-first.
5. **Completion:** tests-only vs tests + same-surface artifact verification.
6. **Continuity:** prose handoff vs persistent state + pickup reconstruction.
7. **Autonomy:** open-ended execution vs explicit exit predicate + reversible-work ownership.
8. **Parallelism:** generic fan-out vs graph-aware frontier + selected orchestration shape.

## What is verified now

Verified by source inspection:

- the named upstream files and mechanisms exist at the pinned snapshots;
- the two projects encode materially different orchestration and persistence choices;
- the mechanisms above can be normalized into the shared skill-anatomy framework.

Not verified yet:

- which mechanism produces better outcomes;
- whether any apparent complementarity survives runtime use;
- whether portability claims hold outside native hosts;
- what amount of process is optimal for FIRST tasks.

Those questions belong to executable experiments.
